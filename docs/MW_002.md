# Part A — Company Registration (Full Stack)

## A1. Entry point & flow

`/signup` → **"Join as a Shipping Company"** → `/signup/company` (replaces the "Coming soon" placeholder).

```
Step 1 Account & Company → Step 2 Services → Step 3 Documents → Step 4 Review & Submit
   → Email OTP verification → "Application submitted" screen (status: Pending review)
```

- Progress indicator with step names; clicking a **completed** step goes back to it.
- **Next** validates the current step only; **Back** never loses data.
- **Autosave draft** of text fields to `localStorage` (never passwords or files); "Continue your application?" prompt on return; cleared after successful submit.
- Leaving the page with unsaved changes shows a confirmation.

## A3. Backend

| Method | Path                      | Purpose                                            |
| ------ | ------------------------- | -------------------------------------------------- |
| POST   | `/api/companies/register` | `multipart/form-data`: application JSON + files    |
| POST   | `/api/auth/verify-email`  | Reuse existing OTP verification (purpose `signup`) |
| POST   | `/api/auth/resend-otp`    | Reuse existing resend                              |

**`/api/companies/register` must:**

1. Validate everything with the **shared Zod schema** (same as frontend), including conditional rules.
2. Check uniqueness: email, phone (all accounts), commercial register number, tax number (companies).
3. Validate files by **real content (magic bytes)**, not extension; enforce size limits.
4. Create the auth user (unconfirmed) with role `company`, the company record, its service details and document records; upload files to storage.
5. **All-or-nothing:** if any step fails, delete everything already created (user, rows, files).
6. Send the signup OTP and return a neutral success.

**Application status lifecycle** (stored now, admin review UI comes later):
`pending_verification` → `pending_review` → `approved` | `rejected` | `changes_requested`. Every status change is recorded in a history log with timestamp and actor.

## A4. Data to store (everything — later plans depend on it)

Use Supabase migrations. Store **every field** from the form plus metadata:

| Data group            | Contents                                                                                                                                                       |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Account               | Auth user, role `company`, email, phone, email verified at                                                                                                     |
| Company profile       | Legal name, representative name + title, contacts (WhatsApp, landline, website), full address, years in business, logo path, notes                             |
| Activities & services | Selected activities, other-activity text, international modes + services + regions, domestic governorates + vehicle types + fleet size, China sites + services |
| Legal                 | Commercial register number, tax number                                                                                                                         |
| Documents             | Type, storage path, original name, MIME, size, uploaded at                                                                                                     |
| Application           | Status, reference number, submitted at, status history                                                                                                         |
| Consent & audit       | Declaration accepted at, terms version accepted, submit IP, user agent                                                                                         |

Keep services in **structured, queryable fields** (not one text blob) — we will match orders to companies by service, mode and governorate later.

## A5. Security

- All rules from the previous task apply (validation, rate limiting, RLS, no enumeration, secrets server-side only).
- **Storage:** private bucket `company-documents`; files renamed to random UUIDs; **no public URLs**; admins will access via short-lived signed URLs only. Logo may go to a separate public bucket.
- Upload limits: max 4 files per request, 5 MB each, allowed types only; reject anything else server-side.
- Rate limit `/api/companies/register`: 3 per hour per IP.
- RLS: a company can read its own application and documents metadata; **cannot change status**, legal numbers or documents after submission (changes only through a future "changes requested" flow).
- Never log document contents, passwords or OTPs.

## A6. Login behavior (implemented in the next plan — design for it now)

Companies will log in from the **same `/login` page** as customers (email or phone + password). After login the app routes by role: `customer` → customer portal, `company` → company portal. In this plan, make sure:

- The role is stored and returned with the session.
- A company account can **never** open the customer portal (route guard by role).
- Until the company portal exists, a company that logs in sees a simple **"Application status"** page (pending / approved / rejected).

- **Desktop:** fixed sidebar (collapsible to icons). **Tablet:** collapsed by default. **Mobile:** bottom navigation with the 4 items + drawer for the rest.
- Sidebar is on the **right in Arabic** and the left in English.
- **Top bar:** page title, notifications bell (unread count), avatar menu (name, Account, Language AR/EN, Logout).
- Every page handles **loading (skeletons), empty and error** states.

## B2. Mock data layer (important)

- All data comes from a service layer (`services/api`) using **TanStack Query**, backed by **MSW (Mock Service Worker)** with realistic fixtures and ~400 ms latency.
- Service function names and response shapes must match the future real API, so switching to the backend later means only removing the mocks.
- Mutations (accept offer, rate company, update profile…) update mock state for the session and show success/error toasts.

## B3. New Request

- Welcome banner: "Welcome, {first name}" with gender-aware icon.
- **Attempts card:** "Remaining requests: X of 5" + progress bar; red state with explanation when 0 (sending is disabled).
- **Draft banner:** "You have an unfinished request" → Continue / Discard.
- **Pre-selected companies chip** when arriving from the directory ("Sending to: Company A, Company B" + remove).
- **3 service cards** (international, domestic, China) — open a placeholder page for now (service forms are a later plan).
- **Success modal component** (ready for later): reference number, assigned companies, Print, Download, "View my orders".

## B4. My Orders

**List**

- Status tabs with counts: All · Awaiting offers · Offers received · Awaiting final approval · In progress · Completed · Cancelled/Rejected.
- Search by order number, sort (newest/oldest), pagination or "load more".
- Order card: number, service, date, status badge, offers count, last update, action ("Details" / "View offers").

**Order details** (`/app/orders/:id`) — tabs:

- **Details:** reference number, status, service, dates, full summary of submitted data, **Cancel request** (with reason, only while allowed).
- **Offers:** anonymous offer cards ("MirhalGo Partner #001"), total cost, offer details, **Accept** (confirm modal: _"Your selection is preliminary until final approval"_), **Reject** (optional reason), **Ask a question** (modal). **Compare offers** side-by-side view when 2+ offers. Banners for "selected — awaiting approval" and "approved — in progress".
- **Timeline:** status history (submitted → under review → offers received → selected → approved → in progress → completed) with dates.

## B5. Companies Directory

- Intro banner, search, category filters (International · Customs clearance · SHEIN/China · Domestic), sort (top rated · most completed · name), results count.
- Company card: logo/initials, name, "Top rated" badge, categories, stars + rating, reviews count, completed orders, **View profile**, **Send request**, select checkbox.
- **Bulk bar:** "X selected" → Clear / Send request to selected; plus "Send to all companies in this category".
- **Company profile:** header, categories, rating, stats, services summary, covered areas, **Send request**, reviews list (like/dislike, sort newest/top).
- **Rate this company:** stars (required, labels Poor → Excellent) + comment (optional, max 500). Enabled **only** for companies that completed an order for this customer; otherwise disabled with explanation.

> **Pending product decision:** offers hide company identity while the directory shows names. Build the directory as specified but keep company-identity display behind one config flag so the decision can change without rework.

## Acceptance Criteria

**Part A — Company registration**

- [ ] 4-step form with all fields above, conditional Step 2, step skipping, draft autosave, review step with edit links.
- [ ] Same validation rules on client and server (shared schema).
- [ ] Files validated by content and size on the server; stored in a private bucket with random names.
- [ ] Registration is atomic — a failure leaves no partial user, rows or files.
- [ ] OTP verification works; application ends in `pending_review`; confirmation email sent.
- [ ] **Every submitted field and document is stored** in structured form with audit metadata.
- [ ] Duplicate email, phone, commercial register or tax number is rejected.
- [ ] Company accounts cannot access customer routes.
- [ ] Rate limits and RLS in place; no secrets in the frontend.

**Part B — Customer portal**

- [ ] Sidebar layout responsive (desktop / tablet / mobile bottom nav) and correct in RTL and LTR.
- [ ] All sections in B3–B8 implemented with mock data, loading/empty/error states and toasts.
- [ ] Mock layer uses MSW + TanStack Query with API-shaped responses.
- [ ] No hard-coded colors or text (design tokens + i18n files).
- [ ] Lighthouse mobile ≥ 90 on the portal pages.
